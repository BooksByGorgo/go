# Types and Variables

Go's type system will feel familiar to a Java programmer but has several sharp edges: every variable has a meaningful zero value from birth, numeric types never coerce implicitly, and the capitalization of one letter can change a type from private to public.
This chapter covers the basic types, how to declare variables, constants, the handful of built-in functions that round out the type system, and structs --- Go's primary mechanism for grouping data, attaching behavior, and composing types.

## Basic Types

\index{basic types}

Go's primitive types map roughly to Java's, with a few differences worth noting.

### Integer Types

\index{int}\index{int8}\index{int16}\index{int32}\index{int64}
\index{uint}\index{uint8}\index{uint16}\index{uint32}\index{uint64}

| Go type | Width | Java equivalent |
|---|---|---|
| `int` | Platform-native (32 or 64 bit) | `int` (always 32 bit in Java) |
| `int8` | 8 bit | `byte` |
| `int16` | 16 bit | `short` |
| `int32` | 32 bit | `int` |
| `int64` | 64 bit | `long` |
| `uint`, `uint8`, `uint16`, `uint32`, `uint64` | Unsigned variants | No direct equivalent |

`int` is the idiomatic integer type for general use.
Its width matches the platform's native word size --- 64 bits on every modern system you will care about.

::: {.tip}
**Wut:** In Java, `int` is always 32 bits.
In Go, `int` can be 32 or 64 bits depending on the platform.
If you need a guaranteed 32-bit integer, use `int32`.
:::

### Floating-Point Types

\index{float32}\index{float64}

`float32` and `float64` correspond to Java's `float` and `double`.
The same as Java: prefer `float64` for most uses.

### Boolean and String

\index{bool}\index{string}

`bool` and `string` are the same concept as Java.
In Go, strings are **immutable byte sequences** (not character sequences --- that distinction matters a lot and gets its own chapter).
`true` and `false` are the only bool literals, same as Java.

### `byte` and `rune`

\index{byte}\index{rune}

`byte` is an alias for `uint8`.
`rune` is an alias for `int32` and represents a Unicode code point.
These two types come up constantly when working with text.

```go
var b byte = 'A'   // b == 65
var r rune = '🎵'  // r == 127925
```

A full treatment of strings, bytes, and runes is in Chapter 3.

## `var` Declarations and `:=`

\index{var declaration}
\index{short variable declaration}

Go has two ways to declare a variable.

### `var`

```go
var name string
var count int = 0
var ratio float64 = 1.5
```

`var` works anywhere --- inside or outside a function.
When you provide an initializer, the type is optional:

```go
var title = "Lose Control"  // type inferred as string
```

### `:=` Short Declaration

\index{:=}

Inside a function body you can use the short declaration operator:

```go
artist := "Teddy Swims"
streams := 4_200_000
```

The compiler infers the type from the right-hand side.
`:=` is the idiomatic choice inside functions; `var` is preferred for package-level variables and when you want to declare a variable without an initial value.

::: {.tip}
**Trap:** `:=` is only valid **inside a function**.
Using it at package level is a syntax error.
:::

### When to Use Each

Use `:=` when you have an initializer and you are inside a function --- it is shorter and more readable.
Use `var` when you want to declare a variable at its zero value, when you need a package-level variable, or when the explicit type improves clarity.

### Redeclaration with `:=`

`:=` can appear on the left side with variables that already exist in the current scope, **as long as at least one variable on the left is new**.
The following example shows how you can reuse `err` across a chain of calls:

```go
n, err := fmt.Println("first")
m, err := fmt.Println("second")  // err already declared; m is new --- OK
n, err := fmt.Println("third")   // error because n and err are already declared
```

If every variable on the left already exists in scope, `:=` is a compile error.

## Zero Values

\index{zero value}

In Java, a local variable that you declare but do not initialize is a compile error.
In Go, every type has a **zero value** that variables are initialized to automatically.

| Type | Zero value |
|---|---|
| `int`, `int8` ... `int64` | `0` |
| `uint`, `uint8` ... `uint64` | `0` |
| `float32`, `float64` | `0.0` |
| `bool` | `false` |
| `string` | `""` (empty string) |
| Pointer, slice, map, channel, function, interface | `nil` |

```go
var count int       // 0
var name string     // ""
var active bool     // false
```

Zero values make it safe to use a variable before assigning to it.
Structs are zero-valued field by field.

### nil

\index{nil}
`nil` is the zero value for the six reference-like type categories listed above.
It is Go's counterpart to Java's `null`, but with two important differences.

First, `nil` only applies to those six types.
Trying to assign `nil` to an `int` or `bool` is a compile error --- those types have their own zero values.

Second, `nil` is often safe and useful rather than a source of panic.
A nil slice has length zero and works correctly with `len`, `range`, and `append`.
A nil map can be read from (the result is always the zero value for the value type).
These behaviors are covered in detail when slices and maps (both Chapter 6) are introduced.

The one nil that always panics is a **nil pointer dereference** --- the same as Java's `NullPointerException`:

```go
var p *int
fmt.Println(p)  // <nil>
fmt.Println(*p) // panic: runtime error: nil pointer dereference
```

Pointer nil is covered fully in Chapter 2.

::: {.tip}
**Tip:** Design your types so the zero value is useful.
A `strings.Builder` at its zero value is an empty, ready-to-use builder --- no constructor call needed (covered in Chapter 3).
:::

::: {.tip}
**Wut:** Java's `null` can be assigned to any reference type and causes a `NullPointerException` on any access.
Go's `nil` is type-specific: a nil slice or map is genuinely usable, whereas a nil pointer panics on dereference.
:::

## Integer Literal Prefixes and the Digit Separator

\index{integer literal prefixes}
\index{digit separator}

Go supports the same literal prefix syntax you may know from modern Java:

```go
bin  := 0b1010_1100   // binary, underscores allowed
oct  := 0o755         // octal (always 0o, never plain 0)
hex  := 0xDEAD_BEEF   // hexadecimal
big  := 1_000_000     // one million, easier to read
```

The underscore `_` is a digit separator --- it is ignored by the compiler and exists only for readability.
You can place it anywhere inside a numeric literal, but not at the start or end.

::: {.tip}
**Wut:** Go uses `0o` for octal, not a leading zero.
`010` in Go is the integer ten, not eight.
Java's `010` is octal eight --- the opposite convention.
:::

## Constants

\index{const}

Constants in Go are declared with `const`.
They can be typed or untyped:

```go
const Pi float64 = 3.14159   // typed constant
const E  = 2.71828           // untyped floating-point constant
```

Untyped constants are precise and flexible --- the compiler treats them as arbitrary-precision numbers and assigns a concrete type at the point of use.

```go
const Streams = 1_200_000_000  // untyped integer constant

var plays32 int32   = Streams  // concrete type: int32
var plays64 int64   = Streams  // same constant, now int64
var ratio   float64 = Streams  // same constant, now float64
```

A typed constant like `Pi float64` can only be used where `float64` is expected.
`Streams` works as any numeric type that can represent its value.

### `iota` and const blocks

\index{const block}

Constants can also be declared in a block.
For example

```go
const (
    Rock = 1
    Pop = 2
    HipHop = 3
    Regeton = 4
)
```

but what about this code?

```go
const (
    Rock = 1
    Pop
    HipHop
    Regeton
)
```

You would think this would be a syntax error or the constants would be set to the same values as the previous example.
It turns out that there is a third option.
The Go Language spec states that if the initialization expression is missing for a constant in a const block, the expression used will be "equivalent to the textual substitution of the first preceding non-empty expression list and its type if any" [@gospec, sec. "Constant declarations"].
That means the following code will print all ones.

```go
fmt.Printf("%v %v %v %v", Rock, Pop, HipHop, Regeton)
```

So, why the `textual substitution`?
Why give one iota about that rule?
Read on!


\index{iota}

`iota` is an untyped integer constant whose value is the position of a constant specification within a `const` block, starting at zero.

It is Go's idiomatic way to define enumerations.

```go
const (
    Free     = iota  // 0
    Standard = iota  // 1
    Premium  = iota  // 2
    Lossless = iota  // 3
)
```

We can take advantage of the textual substitution rule to simplify the preceding example:

```go
const (
    Free     = iota  // 0
    Standard         // 1
    Premium          // 2
    Lossless         // 3
)
```

The `iota` will be implicitly copied to `Standard`, `Premium`, and `Lossless`.

\index{iota!expressions}

You can use `iota` in expressions to offset the starting value:

```go
const (
    Debut     = iota + 1  // 1
    Sophomore             // 2
    Certified             // 3
)
```

`iota` resets to zero at each new `const` block.

::: {.tip}
**Tip:** Skip value zero with `iota + 1` when zero should represent "unset" or "unknown."
This lets you detect a variable that was declared but never assigned a meaningful position.
:::

::: {.tip}
**Wut:** You can also have comma separated const identifiers with corresponding comma separated initializers.
They are not common because they mess with formatting, and `iota` doesn't increment between comma separated identifiers.
:::

\index{type definition}\index{type alias}

### Type Definitions

```go
type Celsius float64
type Fahrenheit float64
```

`type Celsius float64` creates a **new, distinct type**.
Even though both `Celsius` and `float64` have the same underlying representation, they are different types.
Assignment between them requires an explicit conversion:

```go
var c Celsius    = 100.0
var f float64    = float64(c)   // explicit conversion required
var g float64    = c            // compile error: cannot use c (Celsius) as float64
```

This is intentional.
You cannot accidentally pass a temperature in Fahrenheit where the function expects Celsius.

### Type Aliases

```go
type Seconds = float64  // alias, not a new type
```

An alias introduces a new name for the same type.
`Seconds` and `float64` are interchangeable --- there is no conversion needed.
Aliases are most useful in large-scale refactoring or when bridging packages.

::: {.tip}
**Wut:** `type Celsius float64` and `type Celsius = float64` look almost identical but mean opposite things.
Without `=` you get a new type with conversion rules.
With `=` you get a synonym.
:::

## `new` and `make`

\index{new built-in}\index{make built-in}

Go has two allocation built-ins.
They serve different purposes.

### `new`

`new(T)` allocates memory for a value of type `T`, initializes it to the zero value, and returns a `*T`.
Conceptually, the memory is allocated on the heap --- a region of memory that lives on even after the local scope (block of code) finishes.
In reality, Go does *escape analysis* to see if there is a chance the allocation will be used outside of the local scope.
If not, the memory will be allocated on the stack and will be deallocated once the scope --- usually the function or block of code --- finishes.
If reference will be used outside of the local scope --- it was passed to another function or added to a collection object --- the compiler will allocate the memory on the heap where it will live until there are no more references to it.


```go
p := new(int)    // *int pointing to 0
*p = 42
fmt.Println(*p)  // 42
```

You will see `new` occasionally, but struct literals with `&` are more common in practice:

```go
type Point struct{ X, Y int }
pt := &Point{X: 3, Y: 4}  // same idea; more idiomatic for structs
```

If you've worked in other languages like C or C++, you will see that as a potential for a dangling pointer.

```go
func GenPoint() *Point {
    p := Point{X: 3, Y: 4}
    return &p
}
```

However, with escape analysis, Go is able to see that p needs to survive past the return of the function and allocates p on the heap.

You cannot use `new` to create a ready-to-use map or channel --- `new(map[string]int)` gives you a pointer to a nil map.

::: {.tip}
**Tip:** `new` is for scalar types when you need a pointer.
`make` is for slices, maps, and channels.
:::

### `make`

`make` initializes **slices, maps, and channels** --- the three built-in reference types that need internal setup before use.

```go
m := make(map[string]int)    // empty map, ready to use
s := make([]int, 5)          // slice of length 5, capacity 5
ch := make(chan string, 10)   // buffered channel, capacity 10
```

We are going to save the discussion about make with channels for later, when we talk about channels.
For now we will focus on `map` and slices.

### `make` with `map`

In the following code `mm` and `dm` are the same:

```go
mm := make(map[string]int)
dm := map[string]int {}
```

So when do we use `make` and when do we use the `map` literal?
In this example, there is literally (see what I did there :) ) no difference between the two.
But, there is something that we can do with `make` that we can't do with literals: hint at the size of the map.
`make` can take the expected size as the second parameter.
This is a hint that Go can use when allocating memory for the map to avoid future reallocations if the initial size is to small.

Great! So why would you ever use a map literal?
You can initialize a literal with values!
Here is an example of a `map` of `map`s.

```go
dm := map[string]map[string]int {
    "CMPE 30": {
        "Ben" : 22,
        "Amy" : 88,
        "Fred" :32,
    },
    "CMPE 50": {
        "Qi" : 90,
        "Cal" : 102,
    },
}
```

### `make` with slices

Conceptually, a slice is like an array that can grow and shrink.
Just like with map, you can declare a slice with `make` or a literal.

```go
ms := make([]int, 5)      // length 5, all zeros
ls := []int{1, 2, 3}      // literal, initialized with 1, 2, 3
```

`make` for slices takes up to three arguments: the type, the length, and an optional capacity.

```go
s := make([]int, 3, 10)  // length 3, capacity 10
```

**Length** is the number of elements the slice currently holds --- they will be initialized with zero.
**Capacity** is the size of the underlying array --- how many elements it can hold before a new allocation is needed.

This mirrors Java's `new ArrayList<>(initialCapacity)`: you are not filling the slice, you are pre-allocating room so that `append` calls don't trigger repeated reallocations.

```go
s := make([]int, 0, 100)  // empty slice, room for 100 elements
for i := range 100 {
    s = append(s, i)       // no reallocation needed
}
```

Use a literal when you have initial values.
Use `make` when you know the size up front and want to avoid reallocations, or when you need a zero-initialized slice of a specific length.

::: {.tip}
**Tip:** `make([]T, 0, n)` is the idiomatic way to pre-allocate a slice you will fill with `append`.
`make([]T, n)` is for when you want `n` zero-valued elements you will assign by index.
:::

Slices have a lot more to them --- backing arrays, slicing expressions, the `copy` built-in --- and get their own chapter.

## Built-in `min`, `max`, and `clear` (Go 1.21)

\index{min built-in}\index{max built-in}\index{clear built-in}

Go 1.21 added three built-ins that Java programmers typically import from utility libraries.

### `min` and `max`

`min` and `max` are type-safe and variadic --- they work on any ordered type and accept any number of arguments:

```go
smallest := min(3, 1, 4, 1, 5)   // 1
largest  := max(3, 1, 4, 1, 5)   // 5
lo       := min(a, b)            // works for float64, string, etc.
```

No `Math.min(a, b)` gymnastics.

### `clear`

`clear` zeroes the elements of a slice or deletes all entries from a map:

```go
nums := []int{1, 2, 3}
clear(nums)        // nums is now [0, 0, 0], len unchanged

scores := map[string]int{"Harry Styles": 99}
clear(scores)      // scores is now an empty map
```

For slices, `clear` zeroes elements but does not change the length.
For maps, it removes all keys.

## The Blank Identifier

\index{blank identifier}

The blank identifier `_` discards any value you do not need.

```go
n, _ := fmt.Println("Hola")  // discard the byte count
```

Go requires you to use every declared variable, so `_` is your escape hatch when a function returns multiple values and you only need some of them.
You can also use it in a `for range` loop to discard the index or value.

::: {.tip}
**Tip:** If you find yourself using `_` for every return value from a function, that is a signal you should reconsider whether you need to call the function at all.
:::

## Structs

\index{struct}
A struct is a composite type that groups named fields together.
In Java, you use a class; in Go, you use a struct.
The critical difference is that structs are **value types** in Go --- assigning a struct copies all its fields --- whereas in Java every object variable is a reference.

### Struct Definition

\index{struct!definition}
Define a struct type with `type T struct { ... }`:

```go
type Track struct {
    Title    string
    Artist   string
    BPM      int
    Duration float64 // seconds
}
```

The zero value of a `Track` has `Title = ""`, `Artist = ""`, `BPM = 0`, and `Duration = 0.0`.
You can use a zero-value struct immediately; there is no constructor required.

Fields can have the same type listed once, separated by commas:

```go
type Point struct {
    X, Y float64 // two fields, both float64
}
```

### Struct Literals

\index{struct!literal}
There are two forms of struct literal.

**Named form (preferred):**

```go
t := Track{
    Title:    "Timeless",
    Artist:   "The Weeknd & Playboi Carti",
    BPM:      138,
    Duration: 208.0,
}
```

**Positional form (fragile):**

```go
t := Track{"Timeless", "The Weeknd & Playboi Carti", 138, 208.0}
```

::: {.tip}
**Trap:** The positional form breaks silently if you ever add, remove, or reorder fields.
The named form is explicit and resilient to future changes.
Use positional form only for tiny, stable types like `Point{1.0, 2.0}` where the meaning is immediately obvious.
:::

**Anonymous structs** are useful for one-off data shapes, especially in tests and temporary groupings:

```go
entry := struct {
    Title  string
    Plays  int
}{"Save Your Tears", 1_800_000_000}

fmt.Println(entry.Title, entry.Plays)
```

### Struct as a Value Type

\index{struct!value type}
Assigning a struct creates an independent copy:

```go
a := Track{Title: "Agora Hills", Artist: "Doja Cat", BPM: 126}
b := a           // b is a copy; a and b are independent
b.BPM = 130
fmt.Println(a.BPM) // 126 --- a is unchanged
fmt.Println(b.BPM) // 130
```

In Java, `a = b` for an object would make both variables point to the same object.
In Go, you get two distinct structs.

When you want shared mutation --- so that changes through one variable are visible through another --- use a pointer:

```go
pa := &Track{Title: "Agora Hills", Artist: "Doja Cat", BPM: 126}
pb := pa           // both point to the same Track
pb.BPM = 130
fmt.Println(pa.BPM) // 130 --- shared!
```

::: {.tip}
**Tip:** Passing large structs to functions by value copies every field.
For structs with many fields or large fields, pass a pointer (`*Track`) to avoid the copy cost and to allow the function to mutate the original.
The rule of thumb from Chapter 5 applies: use pointer receivers when the struct is large or when mutation is required.
:::

### Methods on Structs

\index{struct!methods}
\index{method}
You attach behavior to a struct by defining methods with a **receiver**:

```go
func (t Track) String() string {                    // value receiver
    return fmt.Sprintf("%s by %s (%d BPM)", t.Title, t.Artist, t.BPM)
}

func (t *Track) ScaleBPM(factor float64) {          // pointer receiver
    t.BPM = int(float64(t.BPM) * factor)
}
```

The receiver appears between `func` and the method name.
A **value receiver** gets a copy; a **pointer receiver** gets a pointer to the original and can modify it.

Chapter 5 covers the receiver rules in detail.
The short version: use a pointer receiver when the method needs to mutate the struct, or when the struct is large enough that copying is expensive.
Use a value receiver when the method only reads and the struct is small.

```go
t := Track{Title: "Messy", Artist: "Lola Young", BPM: 118}
fmt.Println(t.String())   // Messy by Lola Young (118 BPM)
t.ScaleBPM(1.1)
fmt.Println(t.BPM)        // 129
```

In Java you might have a `PlayList` class that wraps an `ArrayList<Track>` and exposes methods.
In Go the equivalent is a struct that embeds a slice, with methods attached the same way:

```go
type Playlist struct {
    Name   string
    tracks []Track  // unexported: only this package can modify it directly
}

func (p *Playlist) Add(t Track) {         // pointer receiver: mutates the slice
    p.tracks = append(p.tracks, t)
}

func (p Playlist) Len() int {             // value receiver: read-only
    return len(p.tracks)
}

func (p Playlist) AverageBPM() float64 { // value receiver: read-only
    if len(p.tracks) == 0 {
        return 0
    }
    total := 0
    for _, t := range p.tracks {
        total += t.BPM
    }
    return float64(total) / float64(len(p.tracks))
}
```

```go
pl := Playlist{Name: "Late Night Vibes"}
pl.Add(Track{Title: "Messy",      Artist: "Lola Young",   BPM: 118})
pl.Add(Track{Title: "MOTOMAMI",   Artist: "Rosalía",      BPM: 127})
pl.Add(Track{Title: "Golden Hour", Artist: "JVKE",         BPM: 97})
fmt.Println(pl.Len())           // 3
fmt.Printf("%.1f BPM\n", pl.AverageBPM()) // 114.0 BPM
```

::: {.tip}
**Tip:** `Add` uses a pointer receiver because it modifies the struct (appending to the slice).
`Len` and `AverageBPM` use value receivers because they only read.
For consistency --- since at least one method needs `*Playlist` --- all methods on this type should use `*Playlist`; see Chapter 5 for the full rule.
:::

::: {.tip}
**Wut:** Making `tracks` unexported (lowercase) is deliberate.
Callers can only grow the playlist through `Add`, which lets you add validation later without changing the public API.
If `tracks` were exported, any package could append to it directly, bypassing any future checks.
:::

### Struct Tags

\index{struct!tags}
\index{struct tags}
A struct tag is a raw string literal attached to a field declaration after the type:

```go
type Track struct {
    Title    string  `json:"title"`
    Artist   string  `json:"artist"`
    BPM      int     `json:"bpm,omitempty"`
    Duration float64 `json:"duration_sec,omitempty"`
}
```

Tags are metadata for the field.
The tag string has no effect at runtime unless a package reads it via reflection.
The `encoding/json` package reads `json` tags to control serialization:

- `json:"title"` uses `title` as the JSON key instead of the Go field name.
- `omitempty` omits the field from the JSON output when its value is the zero value.
- `json:"-"` tells the encoder to skip the field entirely.

The same mechanism is used by other packages:
- `xml:"..."` for `encoding/xml`
- `db:"..."` for database/ORM packages (e.g., `sqlx`, `gorm`)
- `validate:"..."` for validation libraries

\index{reflect.StructTag}
Packages parse tags through the `reflect.StructTag` type, which provides a `Lookup(key string) (value string, ok bool)` method.
You do not need to use reflection yourself to benefit from struct tags --- you just write the tag and the library handles it.

```go
package main

import (
    "encoding/json"
    "fmt"
)

type Playlist struct {
    Name   string  `json:"name"`
    Owner  string  `json:"owner"`
    Tracks int     `json:"track_count,omitempty"`
}

func main() {
    p := Playlist{Name: "Late Night Vibes", Owner: "bcr33d", Tracks: 42}
    data, _ := json.Marshal(p)
    fmt.Println(string(data))
    // {"name":"Late Night Vibes","owner":"bcr33d","track_count":42}

    empty := Playlist{Name: "Empty Queue", Owner: "bcr33d"}
    data, _ = json.Marshal(empty)
    fmt.Println(string(data))
    // {"name":"Empty Queue","owner":"bcr33d"}  --- Tracks omitted (zero)
}
```

::: {.tip}
**Tip:** Tag syntax is strict: backtick string, `key:"value"` pairs separated by spaces, no commas between pairs.
A malformed tag compiles fine but `go vet` will flag it.
Run `go vet ./...` as part of your build.
:::

### Embedding

\index{struct!embedding}
\index{embedding}
Go has no inheritance, but it has **embedding**: you include one struct type inside another by naming only the type, with no field name.

```go
type Artist struct {
    Name    string
    Country string
}

type Song struct {
    Artist           // embedded --- not a named field
    Title  string
    BPM    int
}
```

`Artist` is embedded in `Song`.
The fields and methods of `Artist` are **promoted** to `Song`: you can access them directly on a `Song` value as if they were declared on `Song` itself.

```go
s := Song{
    Artist: Artist{Name: "Rosalía", Country: "Spain"},
    Title:  "MOTOMAMI",
    BPM:    130,
}

fmt.Println(s.Name)    // Rosalía    --- promoted from Artist
fmt.Println(s.Country) // Spain      --- promoted from Artist
fmt.Println(s.Title)   // MOTOMAMI
```

You can still access the embedded struct directly by its type name:

```go
fmt.Println(s.Artist.Name) // Rosalía --- explicit path also works
```

\index{embedding!method promotion}
Method promotion works the same way.
If `Artist` has a method `Label() string`, then `Song` also has `Label()` via promotion, without any code on `Song`'s side.

```go
func (a Artist) Label() string {
    return fmt.Sprintf("%s (%s)", a.Name, a.Country)
}

fmt.Println(s.Label()) // Rosalía (Spain) --- promoted method
```

::: {.tip}
**Wut:** Embedding looks like inheritance but it is not.
A `Song` is not an `Artist`; it simply contains one and exposes its fields and methods as a convenience.
There is no polymorphism here: you cannot pass a `Song` where an `Artist` is expected.
That is what interfaces are for --- covered in Chapter 7.
:::

You can embed a pointer to a type as well:

```go
type Song struct {
    *Artist          // embedded pointer
    Title string
    BPM   int
}
```

With a pointer embedding, a zero-value `Song` has a nil `Artist` pointer.
Accessing a promoted field on a nil embedded pointer panics.
Make sure the embedded pointer is initialized before use.

Multiple types can be embedded in the same struct.
If two embedded types have a field or method with the same name, the outer struct must access them explicitly through the embedded type name to resolve the ambiguity; otherwise the compiler reports an error.

### The `cmp` Package

\index{cmp package}
\index{cmp.Compare}
\index{cmp.Ordered}
Go 1.21 added the `cmp` package in the standard library.
It provides generic comparison utilities that are useful when sorting slices of structs.

```go
// package cmp
func Compare[T Ordered](x, y T) int // -1 if x < y, 0 if x == y, +1 if x > y
```

`cmp.Ordered` is a type constraint satisfied by all integer types, floating-point types, and `string`.

The practical use case is sorting a slice of structs by a numeric or string field:

```go
import (
    "cmp"
    "fmt"
    "slices"
)

type Track struct {
    Title  string
    BPM    int
}

func main() {
    playlist := []Track{
        {Title: "Gata Only",        BPM: 170},
        {Title: "Starboy",          BPM: 186},
        {Title: "Golden Hour",      BPM: 136},
        {Title: "Until I Found You", BPM: 124},
    }

    slices.SortFunc(playlist, func(a, b Track) int {
        return cmp.Compare(a.BPM, b.BPM)
    })

    for _, t := range playlist {
        fmt.Printf("%s: %d\n", t.Title, t.BPM)
    }
}
// Until I Found You: 124
// Golden Hour: 136
// Gata Only: 170
// Starboy: 186
```

`cmp.Compare` replaces the classic three-way comparison pattern and is safe for floats (it handles NaN consistently).

### The `maps` Package

\index{maps package}
Go 1.21 added the `maps` package to the standard library with utility functions for working with maps.

```go
import "maps"

func Keys[Map ~map[K]V, K comparable, V any](m Map) iter.Seq[K]     // yields each key
func Values[Map ~map[K]V, K comparable, V any](m Map) iter.Seq[V]   // yields each value
func Clone[Map ~map[K]V, K comparable, V any](m Map) Map            // shallow copy of m
```

The most common use is combining `maps.Keys` with `slices.Sorted` to iterate a map in sorted key order without manually building a key slice:

```go
import (
    "fmt"
    "maps"
    "slices"
)

func main() {
    bpm := map[string]int{
        "amapiano": 112,
        "hyperpop": 160,
        "lo-fi":    85,
    }

    for _, genre := range slices.Sorted(maps.Keys(bpm)) {
        fmt.Printf("%s: %d\n", genre, bpm[genre])
    }
}
// amapiano: 112
// hyperpop: 160
// lo-fi: 85
```

`maps.Clone` makes a shallow copy of a map --- useful when you want to mutate a map without affecting the original.

## Pointers

\index{pointer}
Java hides pointers --- every object variable is secretly a reference to heap memory, but the language never lets you see or manipulate the raw address.
Go makes pointers explicit: `&` takes an address and `*` follows it.
Understanding Go pointers helps you predict when a function can modify its caller's data, and why some methods need a `*T` receiver rather than a plain `T` receiver.

### `&` and `*` --- Address-Of and Dereference

\index{address-of operator}
\index{dereference operator}
\index{pointer!declaring}
Two operators are all you need to work with Go pointers.

```go
&expr   // address-of: produces a pointer to expr
*pExpr  // dereference: follows the pointer to reach the value
```

A **pointer type** names what the pointer points to, with a `*` prefix:

```go
var p *int      // p is a pointer to int; its zero value is nil
var s *string   // s is a pointer to string; also nil
```

Here is the whole idea in one small program:

```go
package main

import "fmt"

func main() {
    x := 42
    p := &x          // p holds the address of x
    fmt.Println(p)   // something like 0xc0000b4008
    fmt.Println(*p)  // 42 --- dereference to get the value
    *p = 99          // write through the pointer
    fmt.Println(x)   // 99 --- x changed because *p and x are the same memory
}
```

\index{pointer!nil}
The zero value of any pointer type is `nil`.
Dereferencing a `nil` pointer causes a runtime panic --- the same kind of `NullPointerException` you know from Java, just with a different name.

```go
var p *int
fmt.Println(p)  // <nil>
fmt.Println(*p) // panic: runtime error: invalid memory address or nil pointer dereference
```

::: {.tip}
**Wut:** In Java, every object variable is secretly a reference (pointer) to heap memory, but the language provides no syntax to get or store the raw address.
In Go, pointers are explicit: you use `&` to take an address and `*` to follow it.
The Java "hidden pointer" and the Go pointer are the same idea --- Go just shows you the machinery.
:::

### Pointers to Basic Types

\index{pointer!to basic type}
Java programmers sometimes wonder why you would ever have a pointer to an `int`.
In Java, primitive `int` is always a value, and you box it into `Integer` when you need reference semantics.
In Go you use `*int` directly --- no boxing, no wrapper class.

```go
func newInt(n int) *int {
    v := n
    return &v   // safe: compiler moves v to the heap if needed (see Escape Analysis)
}

p := newInt(7)
fmt.Println(*p) // 7
```

### No Pointer Arithmetic

\index{pointer!arithmetic}
In C and C++, you can write `ptr + 1` to advance a pointer to the next element in an array.
Go forbids this entirely.

```go
x := 42
p := &x
p++      // compile error: invalid operation: p++ (non-numeric type *int)
p + 1    // compile error: invalid operation: p + 1 (mismatched types *int and untyped int)
```

::: {.tip}
**Tip:** No pointer arithmetic means the compiler and garbage collector always know exactly what a pointer points to.
It also eliminates an entire class of security vulnerabilities (buffer overruns, out-of-bounds reads) that plague C codebases.
If you need to walk through elements, use a slice --- slices carry length and capacity and support range iteration safely.
:::

When you genuinely need unsafe pointer arithmetic (for C interop or performance-critical operations), the `unsafe` package exists, but it earns its name.
That is an advanced topic far outside normal day-to-day Go.

## Key Points

- Go has sized integer types (`int8` through `int64`, unsigned variants); `int` is the idiomatic general-purpose integer and is platform-native width.
- `byte` is an alias for `uint8`; `rune` is an alias for `int32`.
- Declare variables with `var` (anywhere) or `:=` (inside functions only).
- Every type has a zero value; Go never leaves a variable uninitialized.
- Integer literals support `0b` (binary), `0o` (octal), `0x` (hex), and `_` as a digit separator.
- `const` and `iota` are Go's enumeration mechanism; `iota` counts from zero per `const` block.
- `type Celsius float64` creates a new distinct type; `type Celsius = float64` is a synonym.
- `new(T)` returns a zeroed `*T`; `make` initializes slices, maps, and channels.
- `min`, `max`, and `clear` are built-in since Go 1.21.
- `_` discards values you do not need; every declared variable must otherwise be used.
- Structs are value types; assigning a struct copies it; use pointers for shared mutation.
- Prefer named struct literal syntax over positional; positional form breaks on field reordering.
- Methods use value or pointer receivers; pointer receivers allow mutation; value receivers get a copy.
- Struct tags are metadata strings read by libraries via `reflect.StructTag`; `json:"..."` is the most common.
- Embedding promotes fields and methods of the embedded type; it is composition, not inheritance.
- `cmp.Compare` (Go 1.21) provides a generic three-way comparison for ordered types.
- The `maps` package (Go 1.21) provides `Keys`, `Values`, and `Clone`; combine `maps.Keys` with `slices.Sorted` for sorted map iteration without a manual key slice.
